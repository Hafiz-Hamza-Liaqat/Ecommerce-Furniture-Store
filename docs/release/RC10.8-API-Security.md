# RC10.8 Phase 4 — API Security Verification

Date: 2026-07-21  
Mode: Verification and confirmed-defect fixes only

## Verdict

API authentication, tenant isolation, Policy enforcement, CORS, production OpenAPI lockdown, upload validation, error redaction, and rate limiting passed. Nine confirmed defects were reproduced and fixed (including transport protocol, auth empty-body validation, upload envelope/`rawBody` handling, DAM MIME default, session status consistency, and CX write mapping). One confirmed command-idempotency contract gap remains because a durable repair would require an architectural/persistence change prohibited by this phase.

## Authentication and session results

- Every authenticated HTTP operation returned `401 unauthenticated` without a bearer session.
- Invalid/stale sessions returned `401`; logout invalidated the session immediately.
- Registration ignored client-supplied `companyId` and unexpected privilege fields.
- Duplicate registration returned `409`.
- Known and unknown password-reset requests returned the same `200` shape.
- Password reset confirmation rotated the password.
- Email-verification request/confirmation completed for a disposable account.
- MFA enrollment completed through an authenticated account. The Phase 3 harness remains the evidence for challenged sign-in and consumed-token replay rejection.
- Refresh rotation, refresh-family replay revocation, and concurrent-session behavior remain covered by the accepted Phase 3 security harness and identity tests.

## Authorization and IDOR results

- A mismatched `x-company-id` returned `403 company_mismatch`.
- CQRS handlers bind the authenticated company and evaluate module Policy actions before mutation.
- Record-level authorization tests cover company, organization, branch, owner, and missing-resource scopes.
- List tests prove cross-company rows are removed, scoped rows are filtered, and Policy failures fail closed.
- Upload rejected a foreign `companyId` with `403`.
- CX synchronization rejected a snapshot for another `userId` with `403`.
- No separate hidden admin HTTP API was found. Platform operations are Policy-protected CQRS types.

## Input and protocol security

- Malformed JSON returned a structured `400`.
- Unsupported media types now return structured `415 unsupported_media_type`.
- Payloads over 1 MiB now return a complete structured `413 payload_too_large` response rather than resetting the connection.
- Known paths called with an unsupported method now return `405 method_not_allowed` and `Allow`.
- Upload MIME allow-listing rejected `application/x-msdownload`.
- Unknown CQRS types, invalid list pagination, missing records, and tenant mismatch returned stable 4xx errors.
- Error responses contained no stack traces, local paths, password hashes, environment secrets, or signing material.

## CORS, headers, and API discovery

- Production CORS did not reflect `https://evil.example` and did not emit wildcard origin access.
- Production rate limiting returned `429` under repeated authentication failures.
- Development exposed OpenAPI for verification; production returned `404`.
- Security headers remained present on normal responses and are now also emitted on 413/500 transport errors.
- CSP interactions and browser route protections retain the accepted Phase 3 findings.

## CSRF, injection, traversal, and timeout assumptions

- Authentication uses an explicit bearer session from browser local storage, not an ambient authentication cookie. State-changing endpoints require that header, so classic cross-site form CSRF is not applicable; production CORS supplies an additional browser boundary.
- CQRS payloads are passed through structural and domain validators. SQLite repository calls bind parameters rather than concatenating request values into SQL.
- CX filesystem names are derived from the authenticated session user ID and restricted to `[A-Za-z0-9_-]`; upload storage paths use generated asset/version IDs. No audited route accepts a caller-controlled filesystem path.
- The browser API client aborts requests after 30 seconds. Application `TimeoutError` maps to a structured `504`; a transport-level thrown error maps to a sanitized controlled `500`.
- Auth, dispatch, CX, and upload responses do not currently add explicit `Cache-Control`. POST responses are not cacheable by default; deployment proxies must not override this. Adding uniform `no-store` remains optional hardening rather than a reproduced functional defect.

## Confirmed defects

### P4-D1 — Wrong HTTP method returned 404

- Severity: Low
- Reproduction: `GET /api/v1/auth/sign-in`, `GET /api/v1/commands`, `POST /health/live`, and `DELETE /api/v1/cx/workspace`.
- Before: `404 not_found`, with no `Allow` header.
- Expected: `405 method_not_allowed` for an existing path.
- Root cause: route matching considered method and path together, then treated all misses as unknown routes.
- Fix: detect known paths after exact matching and return 405 with the registered methods.
- Validation: four live cases passed; transport regression test passed.

### P4-D2 — Unsupported JSON media type was accepted

- Severity: Medium
- Reproduction: send a JSON string to `POST /api/v1/auth/sign-in` with `Content-Type: text/plain`.
- Before: the body was parsed and authentication ran, returning `403 invalid_credentials`.
- Expected: reject a non-JSON media type before route execution.
- Root cause: transport parsed body bytes without validating content type.
- Fix: non-empty `POST`, `PUT`, and `PATCH` bodies on registered JSON routes now require `application/json`.
- Validation: live request and transport regression test returned `415 unsupported_media_type`.

### P4-D3 — Oversized request reset the connection

- Severity: Medium
- Reproduction: send a JSON body larger than 1,048,576 bytes.
- Before: client received `fetch failed`/connection reset even though a 413 catch path existed.
- Expected: complete structured 413 response.
- Root cause: the body reader destroyed the socket before the response writer ran.
- Fix: drain excess bytes without buffering them, then throw the internal size exception so the server can send 413. Security and CORS headers are included in transport error responses.
- Validation: live 1.1 MiB request and transport regression test returned `413 payload_too_large`.

### P4-D4 — Empty/null auth JSON body returned 500

- Severity: Medium
- Reproduction: `POST /api/v1/auth/sign-in` with empty body or `null`.
- Before: `500 transport_failure`.
- After: `400 transport_validation_failed`.
- Fix: auth routes require a JSON object body before field reads.

### P4-D5 / P4-D6 — Upload envelope and JSON-as-bytes

- Severity: High
- Reproduction: authenticated JSON `POST /api/v1/uploads`; then consume via `ApiClient.upload`.
- Before: bare 202 DTO broke the client contract, and JSON bytes were stored as DAM object content.
- After: shared `{ok,data,correlationId}` envelope; JSON content-type is metadata-only.
- Fix: `packages/api/src/routes/routes.ts`.

### P4-D7 — DAM UI defaulted to disallowed MIME

- Severity: Medium
- Reproduction: create DAM asset with blank MIME through ERP ModuleApp.
- Before: defaulted to `application/octet-stream` → API `400`.
- After: client requires an explicit allowlisted MIME.
- Fix: `packages/web/src/modules/erp/ModuleApp.tsx`.

### P4-D8 — Invalid sessions returned 403 on CQRS/CX

- Severity: Low
- Reproduction: bad Bearer against `/api/v1/commands` vs `/api/v1/auth/session`.
- Before: commands/CX returned `403 session_invalid`; auth routes returned `401`.
- After: session-auth failures return `401` with the original session code.
- Fix: shared unauthorized mapping in dispatch and CX gates.

### P4-D9 — CX write failures were mapped as authorization 403

- Severity: Low
- Reproduction: force a non-writable CX sync directory and PUT a valid snapshot.
- Before: `403` with store/`Error.message` content.
- After: generic `503 cx_sync_write_failed` without filesystem path leakage.
- Fix: map write failures through `InfrastructureError`.

## Remaining security/data-integrity risk

### P4-R1 — Accepted idempotency key does not deduplicate commands

- Severity: High
- Reproduction: send identical `sales.CreateOpportunity` commands twice with the same `idempotencyKey`.
- Actual: both requests returned `200` with different opportunity IDs.
- Risk: client retries can duplicate writable business operations.
- Why not fixed: correct production behavior requires a durable, tenant/user/type/key-scoped idempotency record, request fingerprint comparison, atomic claim, cached result, expiry policy, and multi-process semantics. An in-memory map would give a false guarantee and would not survive restarts or multiple hosts. Adding durable infrastructure or schema is outside the explicit Phase 4 constraints.
- Required follow-up: approve a separately designed durable idempotency implementation before claiming that `idempotencyKey` is enforced. Until then, clients must not treat the field as a retry guarantee.
