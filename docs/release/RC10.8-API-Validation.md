# RC10.8 Phase 4 — API Validation and Contract Results

Date: 2026-07-21

## Result

The final live harness passed 21/21 scenarios after nine minimal confirmed-defect fixes. It exercised all 20 concrete HTTP operations, representative CQRS create/read/update/list behavior, invalid input, missing resources, tenant isolation, upload validation, synchronization concurrency, frontend compatibility, and production-profile controls.

## Request validation matrix

| Case | Observed behavior |
|---|---|
| Missing/empty body | Structured `400` after authentication for protected routes |
| Malformed JSON | `400` with `invalid_json`; no crash or stack |
| Wrong top-level types | Structured `400` from transport DTO validation |
| Missing `commandType` / `queryType` / `payload` | `400` validation issues |
| Unknown command/query type | `404` stable error |
| Invalid enum/business field | `400` from module validator |
| Invalid paging | `400`; page must be >= 1 and size 1–500 |
| Oversized body | `413 payload_too_large` with maximum in details |
| Unsupported media type | `415 unsupported_media_type` |
| Unexpected registration properties | Ignored; no company/role mass assignment |
| Foreign company header/payload | `403 company_mismatch` / Policy denial |
| Invalid upload MIME | `400 not_allowed` |
| Invalid sync version/shape | `400` |
| Foreign sync user | `403` |

The generic dispatch DTO validates the envelope while each application validator validates the domain payload. Unexpected domain properties are not copied into persisted entities unless explicitly read by a handler. Restricted fields are additionally covered by field-authorization tests.

## Response contract checks

- Success and error responses use `application/json; charset=utf-8`.
- CQRS success is `{ok:true,data,correlationId}` and includes `x-correlation-id`.
- Errors use `{error:{code,category,message,details,retryable,correlationId}}`.
- Registration returned `201`; CORS preflight returned bodyless `204`.
- Missing records returned `404`; validation returned `400`; authentication returned `401`; authorization returned `403`; duplicates returned `409`; business-rule failures mapped to `422`; rate limiting returned `429`.
- Known path/wrong method returned `405` plus `Allow`.
- Application timeout errors mapped to `504`. A deliberately thrown transport error returned a sanitized controlled `500` with empty details and no stack, path, or secret.
- No tested response leaked stack traces, source paths, password hashes, environment secrets, or signing keys.
- Empty list responses remained stable with `items:[]`, `totalCount:0`, paging values, `nextCursor:null`, and `hasMore:false`.
- Timestamps were ISO-8601 strings and nullable fields remained explicit where defined by the module DTO.
- Browser fetch through the Vite proxy successfully consumed the same query envelope used by `ApiClient`.

## CRUD and persistence

The live representative sales flow completed:

1. `sales.CreateOpportunity` returned an `opportunityId`.
2. `sales.GetOpportunity` returned the persisted title.
3. `sales.UpdateOpportunity` changed the title.
4. `sales.ListOpportunity` found the updated record using search and explicit pagination.

Sales opportunities intentionally have no delete/archive command. Deletion was therefore not invented for the audit. Module-specific CRUD/lifecycle behavior is covered by application handler suites:

- projects uses `projects.ArchiveProject`;
- orders use lifecycle cancellation rather than deletion;
- workflow/approval types transition state;
- collaboration notes/attachments provide explicit delete/detach;
- immutable ledger, stock, payment, and audit-like operations do not expose destructive deletion.

Upload persistence returns an asset ID in the shared `{ok,data,correlationId}` envelope after company and MIME validation. JSON metadata uploads are treated as metadata-only drafts; they no longer persist the JSON body as DAM object bytes.

## Error handling

Forced failures included:

- duplicate registration (`409`);
- invalid credentials (`403`, existing authentication contract);
- stale/logout session (`401`);
- missing sales opportunity (`404`);
- unknown CQRS type (`404`);
- invalid pagination (`400`);
- company mismatch (`403`);
- unsupported upload MIME (`400`);
- malformed and foreign sync snapshots (`400`/`403`);
- production authentication flood (`429`);
- unsupported methods and media (`405`/`415`);
- excessive body size (`413`).

All responses were intentional, structured, and redacted. No unhandled 500 was observed in the final run.

## Synchronization and concurrency

- Anonymous GET/PUT was rejected.
- Snapshot `userId` was bound to the session and foreign identity was rejected.
- Invalid versions/shapes were rejected before persistence.
- Ten simultaneous valid writes completed without corruption; the final snapshot was complete and belonged to the authenticated user.
- Server persistence is last-completed-write-wins. Semantic record conflict resolution remains in the RC10.5 client synchronization engine. The server does not expose optimistic concurrency tokens or a 409 revision conflict contract.

## Duplicate command behavior

Two identical create commands with the same accepted `idempotencyKey` both succeeded with different IDs. This is recorded as P4-R1. It was not repaired because a correct durable multi-host implementation requires architecture/persistence work prohibited by this audit.

## Performance baseline

Thirty measured requests per operation were captured after warm-up on the local development host:

| Operation | Mean | p95 | Max | Response bytes | Compression |
|---|---:|---:|---:|---:|---|
| Health live | 0.60 ms | 1.06 ms | 1.50 ms | 38 | None |
| Auth session | 39.69 ms | 51.71 ms | 60.73 ms | 4,982 | None |
| Sales list (25 requested) | 98.17 ms | 112.70 ms | 134.30 ms | 10,421 | None |
| CX workspace | 4.25 ms | 5.17 ms | 17.84 ms | 323 | None |

This is documentation only. The sales list was the slowest measured endpoint but did not cross a defined failure threshold. No optimization was made. Compression is not enabled on the direct Node host; this should normally be supplied by the production reverse proxy for larger responses.

## Data-integrity conclusion

No corruption was observed in the representative CQRS, upload, or synchronization flows. Existing application suites remain the primary exhaustive evidence for sales, CRM, projects, procurement, inventory, finance, manufacturing, HR, service, CMS, DAM, notifications, reporting, search, workflow, approvals, collaboration, bulk I/O, and jobs. Planner/configurator calculations and browser-local analytics were not mutated by the API harness.
