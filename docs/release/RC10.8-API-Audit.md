## Defects found and fixed

### P4-D1 — Wrong HTTP method returned 404

- Severity: Low
- Before: known paths with unsupported methods returned `404 not_found`
- After: `405 method_not_allowed` with `Allow`
- Fix: `packages/api/src/transport/node-http.ts`

### P4-D2 — Unsupported media type accepted

- Severity: Medium
- Before: `text/plain` bodies were parsed as JSON and processed
- After: `415 unsupported_media_type` before route execution
- Fix: `packages/api/src/transport/node-http.ts`

### P4-D3 — Oversized body reset the connection

- Severity: Medium
- Before: bodies over 1 MiB caused client connection reset
- After: complete `413 payload_too_large` response with security/CORS headers
- Fix: drain excess input without buffering, then return the structured 413

### P4-D4 — Empty/null auth JSON body returned 500

- Severity: Medium
- Before: empty or `null` bodies on auth routes crashed into `transport_failure`
- After: structured `400 transport_validation_failed`
- Fix: `packages/api/src/routes/auth-routes.ts` validates a JSON object before field reads

### P4-D5 — Upload success envelope broke `ApiClient`

- Severity: High
- Before: `POST /api/v1/uploads` returned a bare DTO; `ApiClient.upload` required `{ok:true,data,correlationId}`
- After: `202` uses the shared success envelope
- Fix: `packages/api/src/routes/routes.ts`

### P4-D6 — JSON upload metadata was stored as file bytes

- Severity: High
- Before: Node transport `rawBody` contained the JSON metadata and DAM stored it as an object version
- After: the JSON HTTP upload contract is metadata-only (`rawBody` null); asset bytes are not inferred from its request body
- Fix: `packages/api/src/routes/routes.ts`

### P4-D7 — DAM create UI defaulted to a disallowed MIME

- Severity: Medium
- Before: blank MIME fell back to `application/octet-stream`, which the allowlist rejects
- After: blank MIME is rejected client-side before upload
- Fix: `packages/web/src/modules/erp/ModuleApp.tsx`

### P4-D8 — Invalid sessions returned 403 on CQRS/CX while auth routes returned 401

- Severity: Low
- Before: `session_invalid` on commands/CX used Authorization→403
- After: session-auth failures return `401` with the original session code
- Fix: `packages/api/src/routes/routes.ts`, `packages/api/src/cx-sync/routes.ts`, `packages/api/src/errors/exception-mapping.ts`

### P4-D9 — CX write failures were mapped as authorization 403

- Severity: Low
- Before: store write exceptions became `AuthorizationError` and could surface filesystem messages
- After: generic `503` infrastructure error `cx_sync_write_failed`
- Fix: `packages/api/src/cx-sync/routes.ts`

## Remaining risks

### P4-R1 — Accepted command `idempotencyKey` is not enforced

- Severity: High
- Evidence: identical create commands with the same key returned different opportunity IDs
- Why deferred: durable, multi-host, fingerprint-aware idempotency storage would change architecture/persistence beyond Phase 4 constraints
- Guidance: clients must not treat `idempotencyKey` as a retry guarantee until a dedicated durable implementation is approved

Additional accepted residual items from Phase 3 remain unchanged (single-round password hashing, frontend route-guard disable via localStorage, auth-adjacent default rate bucket).
