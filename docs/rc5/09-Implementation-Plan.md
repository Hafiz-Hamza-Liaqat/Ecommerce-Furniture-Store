# RC5 — Implementation Plan (RC5.1–RC5.9)

**Constraint:** Incremental delivery. No architecture redesign. No new authorization framework. No invented List*/Workflow query APIs.

---

## RC5.1 — Authorization foundation

| | |
|---|---|
| **Scope (locked)** | Permission catalog; role catalog; canonical permission constants; versioned/idempotent seed data; role-permission and legacy-action mappings; permission-definition tests |
| **Dependencies** | Identity SQL store; RbacService; Policy Engine |
| **Risk** | Incomplete seeds → false denials; over-broad grants |
| **Rollback** | Restore pre-seed catalog/role-link snapshot; deactivate the new catalog version; do not remove tenant custom roles |
| **Compatibility** | Seed 105 canonical backend permissions, map every one of the 105 current executable action keys exactly once, and keep Policy exact-match working by dual-granting/compatibility seeding the legacy keys; do not rename handlers |
| **Acceptance** | Canonical grammar passes; 33 system roles and hierarchy are deterministic; 107 handlers/105 legacy keys map without gaps; a principal granted a mapped permission can satisfy current handler action strings; repeated seed is idempotent; permission-definition tests and seed audit pass |
| **Complexity** | Medium |

### RC5.1 frozen scope lock

RC5.1 may **only** deliver:

1. permission catalog;
2. role catalog;
3. permission constants;
4. seed data;
5. canonical permission, role-permission, and legacy-action mapping;
6. permission-definition and seed-integrity tests.

RC5.1 must **not**:

- protect or change routes;
- modify navigation or menu visibility;
- hide or disable UI;
- enforce module permissions on new surfaces;
- change handler action strings or existing Policy evaluation order/behavior;
- implement record-level security;
- implement field-level security;
- activate workflow/approval enforcement;
- assign production users as part of the milestone deliverable;
- add APIs, migrations generated by this documentation pass, frameworks, or architecture.

Any pull request containing excluded work is not RC5.1 and must be split or rejected. RC5.2 owns route/navigation/UI declarations; RC5.4 owns API action normalization/enforcement changes; RC5.5 owns record security; RC5.6 owns field security.

**Implementation evidence (2026-07-17):** RC5.1 is implemented in `packages/identity/src/rbac/catalog/` (catalog version `rc5.rbac-catalog.v1`); see `docs/release/RC5.1-authorization-foundation.md` for the evidence packet.

## RC5.6 — Field-level authorization

| | |
|---|---|
| **Scope** | Field metadata on live API entities; DTO omit/redact; UI hide/disable; finance/HR/KYC priority |
| **Dependencies** | RC5.4–5.5 |
| **Risk** | Over-redaction breaks UX; under-redaction leaks |
| **Rollback** | Flag `field_security_v1` |
| **Acceptance** | Tests prove cost/KYC fields absent under deny; update rejects forbidden patches |
| **Complexity** | Medium–High |

**Implementation evidence (2026-07-18, RC5.6 completion):** Shared application-layer field projection and patch validation delegate every field decision to the existing Policy Engine. Live finance invoice/payment/credit DTOs omit or mask sensitive values; invoice-line and payment restricted fields reject the complete write before persistence; sensitive read/write outcomes are audited without values. `EntityDef.fields` carries presentation-only view/edit/sensitivity metadata. Tests prove finance allow/deny, KYC omission, payment masking, missing-principal and Policy-failure fail-closed behavior, no-partial-mutation, and UI hide/disable behavior. The frozen RBAC catalog, role seeds, routes, sessions, authentication, and Policy Engine algorithm are unchanged. HR/KYC have no live CQRS DTO endpoint, so RC5.6 supplies and tests the shared contract without inventing APIs. Evidence: `docs/release/RC5.6-field-level-security.md`, `docs/release/RC5.6-verification-report.md`, and `docs/release/RC5.6-field-level-security-audit.md`.

| | |
|---|---|
| **Scope** | Execute `10-Test-Plan.md`: unit Policy/RBAC; integration authorize; matrix; unauthorized/direct URL/API-only/IDOR/isolation/escalation/field/read-only/inheritance/deny-precedence/regression/performance coverage |

**Implementation evidence (2026-07-18, RC5.7 completion — approved scope: query/list record filtering):** The approved RC5.7 slice delivered Policy-based result filtering for collection-bearing queries (ADR D46). A shared `filterAuthorizedRecords` helper in `@afh/application` delegates every row decision to the existing Policy Engine; the five company-wide module summary handlers (sales, procurement, inventory, finance, CRM) and their derived id/count projections now include only rows the principal's scopes allow, the collection gate uses principal scope hints (`principalListScope`) so scoped principals get filtered results instead of a blanket deny, and evaluation failures fail the whole query closed. Rows without persisted scope fields stay hidden from scoped principals (missing data denies). Tests: `packages/api/src/authorization/list-filtering.test.ts` (owner/organization/branch/company scopes, cross-company and leaked-row denial, fail-closed). The RBAC catalog, role seeds, sessions, routes, and the Policy Engine algorithm are unchanged. Evidence: `docs/release/RC5.7-list-filtering.md`, `docs/release/RC5.7-verification-report.md`, `docs/release/RC5.7-list-filtering-audit.md`.

## RC5.8 — Documentation

| | |
|---|---|
| **Scope** | Update operator docs; sync productization deltas; publish role→permission cheat sheets; record session/cookie dependency status |
| **Dependencies** | RC5.7 results |
| **Risk** | Docs drift |
| **Rollback** | N/A |
| **Acceptance** | `docs/rc5` + ops notes consistent with shipped behavior |
| **Complexity** | Low–Medium |

**Implementation evidence (2026-07-18, RC5.8 completion — approved scope: permission-to-scope binding in the Policy Engine):** The approved RC5.8 slice delivered the target assignment rule deferred by ADR D45 (see ADR D47). `buildPrincipal` now attaches each role entry's contributed permission codes, and the Policy Engine's scope stage evaluates only the entries that granted the action — a company/global-scoped assignment can no longer widen the scope of a permission granted only by an own/organization/branch assignment. The flat session permission projection, reason codes, RBAC catalog, route protection, and authentication are unchanged; legacy principals without per-entry data keep the pre-RC5.8 behavior, and partially populated principals fail closed. `principalListScope` became action-aware so RC5.7 collection gates derive hints from granting assignments only. Tests: `packages/identity/src/policy/policy-engine.test.ts` (engine binding, hierarchy, super_admin, legacy/partial fallback, unchanged stages) and `packages/api/src/authorization/scope-binding.test.ts` (pipeline cross-role widening closed, owner path preserved, list-filtering interplay). Reports: `docs/release/RC5.8-scope-binding.md`, `docs/release/RC5.8-verification-report.md`, `docs/release/RC5.8-scope-binding-audit.md`.
