# RC5 — Implementation Plan (RC5.1–RC5.9)

**Constraint:** Incremental delivery. No architecture redesign. No new authorization framework. No invented List*/Workflow query APIs.

---

## RC5.1 — Authorization foundation

| | |
|---|---|
| **Scope (locked)** | Permission catalog; role catalog; canonical permission constants; versioned/idempotent seed data; role-permission and legacy-action mappings; permission-definition tests |
| **Dependencies** | Identity SQL store; RbacService; Policy Engine |
| **Risk** | Incomplete seeds → false denials; over-broad grants |
| **Rollback** | Restore pre-seed catalog/role-link snapshot; deactivate the new catalog version; do not remove tenant custom roles |
| **Compatibility** | Seed 105 canonical backend permissions, map every one of the 105 current executable action keys exactly once, and keep Policy exact-match working by dual-granting/compatibility seeding the legacy keys; do not rename handlers |
| **Acceptance** | Canonical grammar passes; 33 system roles and hierarchy are deterministic; 107 handlers/105 legacy keys map without gaps; a principal granted a mapped permission can satisfy current handler action strings; repeated seed is idempotent; permission-definition tests and seed audit pass |
| **Complexity** | Medium |

### RC5.1 frozen scope lock

RC5.1 may **only** deliver:

1. permission catalog;
2. role catalog;
3. permission constants;
4. seed data;
5. canonical permission, role-permission, and legacy-action mapping;
6. permission-definition and seed-integrity tests.

RC5.1 must **not**:

- protect or change routes;
- modify navigation or menu visibility;
- hide or disable UI;
- enforce module permissions on new surfaces;
- change handler action strings or existing Policy evaluation order/behavior;
- implement record-level security;
- implement field-level security;
- activate workflow/approval enforcement;
- assign production users as part of the milestone deliverable;
- add APIs, migrations generated by this documentation pass, frameworks, or architecture.

Any pull request containing excluded work is not RC5.1 and must be split or rejected. RC5.2 owns route/navigation/UI declarations; RC5.4 owns API action normalization/enforcement changes; RC5.5 owns record security; RC5.6 owns field security.

**Implementation evidence (2026-07-17):** RC5.1 is implemented in `packages/identity/src/rbac/catalog/` (catalog version `rc5.rbac-catalog.v1`); see `docs/release/RC5.1-authorization-foundation.md` for the evidence packet.

## RC5.2 — Route authorization

| | |
|---|---|
| **Scope** | Route metadata (permission, scope) for all `/app`, `/portal`, `/admin` routes; nav filtering; forbidden empty states; onboarding guard decision; **no** frontend Policy decisions |
| **Dependencies** | RC5.1 permission codes; session principal permission list from API (existing session/me enrichment or equivalent **without new business APIs** — prefer extending existing session payload if already allowed; if not, identify gap) |
| **Risk** | Deep links still open UI chrome — acceptable if APIs deny; session payload bloat |
| **Rollback** | Flag `ui_route_perms` off → session-only guards |
| **Acceptance** | Matrices in `04` satisfied for explicit routes; ERP generator reads module/entity meta |
| **Complexity** | Medium–High |

**Gap note:** If session endpoint cannot return permission codes today, record as Identity session DTO extension (still Identity package; not a new auth engine). Do not invent a second `/permissions` microservice.

**Implementation evidence (2026-07-17):** RC5.2 route protection is implemented in `packages/web/src/routes/route-permissions.ts`, `packages/web/src/auth/RequirePermission.tsx`, and `packages/web/src/App.tsx` (guard flag `afh.web.routeGuard` / `VITE_ROUTE_PERMISSION_GUARD`); see `docs/release/RC5.2-route-protection.md` for the evidence packet. Nav filtering and dashboard control gating were explicitly deferred (nav filtering to a later approved slice; dashboards to RC5.3).
